# Правила backend-репозитория

Это самостоятельный NestJS backend с Prisma и PostgreSQL. Соблюдать процесс ниже также при работе вне общего workspace.

## Обязательный процесс задачи

1. До любых изменений проверить Git-репозиторий, статус, текущую ветку, remote и целевую ветку PR. Прочитать локальные инструкции, README и относящуюся к задаче документацию.
2. Для новой задачи создать отдельную ветку до редактирования файлов: например, feat/<task>, fix/<task> или docs/<task>. Начинать от актуальной целевой ветки. Продолжение существующей задачи выполнять в её ветке и PR. Не реализовывать задачи и не коммитить напрямую в main/master или другую целевую ветку.
3. Существующие незакоммиченные изменения сохранять. Не сбрасывать, не перезаписывать и не включать постороннюю работу в коммит задачи. Если чистую базу нельзя получить безопасно, использовать отдельный worktree. Если изменения задачи уже начаты на main, перенести их на отдельную ветку до дальнейшей работы.
4. Перед реализацией кратко изложить план: цель, затронутые части, шаги реализации, проверки и обновление документации. Для обычной работы не ждать отдельного подтверждения плана, если пользователь его не запросил.
5. Реализовать задачу в её ветке. Поддерживать актуальную документацию в docs/ и README в том же PR: поведение, архитектуру, API, конфигурацию, миграции и команды запуска по мере изменения. Документация описывает текущее устройство проекта; историю выполнения хранить в Git и PR. Если задача не меняет документируемое поведение, проверить документацию и объяснить в PR, почему правки не требуются.
6. Выполнить подходящие проверки. Для изменений только Markdown проверить ссылки, корректность содержания, UTF-8 и git diff --check; сборка не требуется. Не выдавать непроведённые проверки за успешные.
7. Просмотреть diff, сделать commit только файлов задачи, отправить ветку в GitHub и создать pull request в целевую ветку. Push и создание PR являются стандартным завершением задачи и не требуют повторного разрешения. Если PR этой задачи уже существует, обновлять его, а не создавать новый на каждый коммит.
8. В описании PR указать проблему и результат, основные изменения, обновлённую документацию, фактические проверки, ограничения и необходимые миграции/настройки. Следовать шаблону репозитория. Описание должно быть понятно без переписки; при изменении объёма задачи обновлять заголовок и описание.
9. Проверить, что PR существует на GitHub и содержит нужные коммиты, проверить доступный статус CI, исправить связанные с задачей ошибки и вернуть ссылку со статусом проверок. При отсутствии доступа, инструментов или иных блокерах сохранить подготовленное описание PR и явно сообщить, какой этап не выполнен. Ссылка на ветку или форму создания PR не заменяет готовый PR.
10. Не выполнять merge автоматически. Не публиковать незавершённую работу как готовую. Явные указания пользователя приостановить задачу или не выполнять commit/push/PR имеют приоритет.

Для задачи в нескольких репозиториях создать отдельные ветки и PR в каждом, связать их ссылками и описать порядок совместимого выпуска. Корень workspace без .git не превращать в новый репозиторий ради PR.

## Backend: документация и проверки

- Процесс разработки: [docs/DEVELOPMENT_WORKFLOW.md](docs/DEVELOPMENT_WORKFLOW.md). Запуск и устройство БД: [README.md](README.md) и [docs/DATABASE_GUIDE.md](docs/DATABASE_GUIDE.md).
- Изменения схемы оформлять новой миграцией; не переписывать уже применённые миграции. Описывать применение миграций и совместимость API.
- Для изменений кода использовать npm run build и относящиеся к задаче тесты npm test / npm run test:e2e. Тесты запускать только на изолированной локальной microfronts_test через штатные scripts/test-db.mjs; не очищать рабочую или облачную БД ради тестов.
- Сохранять русские строки и UTF-8; не коммитить .env, секреты и сгенерированный Prisma Client.
