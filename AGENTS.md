# Правила backend-репозитория

Это самостоятельный NestJS backend с Prisma и PostgreSQL. Правила действуют и при работе вне общего workspace.

## Работа над задачей

- До изменений изучить доступные файлы и диагностику, отделить подтверждённую проблему от предположений и предложить короткий план: поведение, затронутые части, проверки, документация и публикация. Дождаться явного согласия пользователя до редактирования кода, конфигурации, тестов и миграций. При существенном изменении плана согласовать его снова.
- До правок проверить Git-статус, ветку, remote и целевую ветку PR. Новую задачу выполнять в отдельной ветке от актуальной целевой ветки; продолжение — в существующей ветке. Явное указание пользователя работать в текущей ветке имеет приоритет. Сохранять чужие изменения и не включать их в commit или PR.
- После согласования реализовать задачу, выполнить относящиеся к ней проверки, обновить документацию при изменении поведения и просмотреть итоговый diff. Непроведённые или упавшие проверки не считать успешными.

Навигация по коду и справочникам: [backend-workflow](.agents/skills/backend-workflow/SKILL.md). Для проектирования, реализации и ревью NestJS-кода применять [nestjs-development](.agents/skills/nestjs-development/SKILL.md). Примеры навыков не расширяют согласованный объём. Обязательные правила процесса хранятся здесь.

## База данных и проверки

- SQL-миграции создавать командой Prisma на основании изменений `schema.prisma`. Не создавать `migration.sql` вручную и не заменять сгенерированный SQL самостоятельно написанным. Сначала генерировать миграцию через `npm run db:migrate -- --name <name> --create-only`, затем просматривать SQL и проверять его перед применением. Если требуется изменение, которое Prisma не генерирует, отдельно обсудить его с пользователем. Применённые миграции не переписывать.
- Изменения схемы оформлять новой миграцией. Не очищать рабочую или облачную БД ради тестов. Перед миграцией проверить целевое подключение без вывода секретов. Потенциально разрушительные изменения согласовывать отдельно. Команды и порядок — в [DATABASE_GUIDE.md](docs/DATABASE_GUIDE.md).
- Тесты с БД запускать только через штатные скрипты на изолированной локальной `microfronts_test`; `npm test` и `npm run test:e2e` выполнять последовательно. Для кода выполнять сборку и относящиеся к задаче тесты; для изменений только Markdown достаточно проверки содержания, ссылок, UTF-8 и `git diff --check`.
- Сохранять русские строки и UTF-8. Не коммитить `.env`, секреты и сгенерированный Prisma Client.

## Публикация

- Если публикация входит в согласованный план и пользователь не ограничил работу локальной веткой, после проверок подготовить commit только файлов задачи, push и новый или существующий PR в проверенную целевую ветку. Проверить состав PR и доступный статус CI; вернуть настоящую ссылку и фактические результаты. При отсутствии доступа сообщить блокер до push.
- Сообщить фактический статус GitHub CI до merge. Railway отдельно собирает и запускает приложение после merge в `main`: успешный CI не подтверждает деплой. При запросе проверки деплоя через Railway-плагин сопоставить его с коммитом, проверить статус и логи сборки, миграций и запуска, сообщить причину или неопределённость. Плагин сам не продолжает чат и не запускает мониторинг. Redeploy, rollback и изменения облачных настроек или БД требуют отдельного плана.
- Не выполнять merge и не удалять ветку без отдельного указания. Для изменений в нескольких репозиториях нужны отдельные ветки и PR в каждом.
