# Процесс разработки backend

Обязательные правила работы с задачами находятся в [AGENTS.md](../AGENTS.md). Этот документ описывает порядок для разработчика; проектный навык агента находится в [.agents/skills/backend-workflow/SKILL.md](../.agents/skills/backend-workflow/SKILL.md).

Архитектурные решения и проверка качества NestJS-кода описаны в [nestjs-development](../.agents/skills/nestjs-development/SKILL.md). Навык дополняет порядок работы: помогает определить владельцев ресурсов, границы модулей, DTO и проверки доступа до реализации. Он не запускает рефакторинг автоматически.

## От задачи до pull request

1. Изучить текущее поведение и согласовать ожидаемый результат и план до изменений.
2. Проверить состояние репозитория и работать в ветке задачи, сохраняя незавершённые изменения других задач.
3. Реализовать согласованный объём, написать нужные тесты и выполнить подходящие проверки. Команды брать из [package.json](../package.json) и сверять с [CI](../.github/workflows/ci.yml). Для PostgreSQL и Prisma соблюдать [руководство БД](DATABASE_GUIDE.md); тестовое окружение описано в [TESTING.md](TESTING.md).
4. Обновить README или документы, если изменились API, данные, конфигурация, запуск или проверка проекта. Перед публикацией просмотреть diff и проверить только файлы задачи.
5. Если публикация согласована, создать или обновить PR по [шаблону](../.github/pull_request_template.md), проверить его состав и статус CI. Merge выполняется отдельно.

Для задачи только с Markdown достаточно проверить содержание, ссылки, UTF-8 и `git diff --check`. Сборка и тесты приложения в этом случае не требуются.

## Описание PR

Укажите проблему и итоговое поведение, основные изменения, документацию, фактически выполненные проверки и ограничения. Для изменений БД опишите миграции и необходимые настройки. Если обязательная проверка не выполнена, не объявляйте задачу завершённой.
