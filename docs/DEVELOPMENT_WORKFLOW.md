# Процесс разработки backend

Правила для агента находятся в [AGENTS.md](../AGENTS.md).

## От задачи до pull request

1. Проверить Git-статус, remote и целевую ветку. Сохранить существующую незавершённую работу.
2. Создать отдельную ветку задачи до изменений. Продолжать уже начатую задачу в её существующей ветке.
3. Кратко сформулировать план реализации, документации и проверок.
4. Реализовать задачу и обновить затронутые документы в docs/ и README в этой же ветке.
5. До итогового коммита пройти порядок проверки Prisma, миграций, тестовой и локальной рабочей БД, приведённый ниже. Проверить итоговый diff.
6. Закоммитить только изменения задачи, отправить ветку в GitHub и создать PR. Обновлять этот PR при дальнейшем изменении задачи.
7. Проверить состав PR и статус CI. Предоставить ссылку и фактические результаты. Merge выполняется только по отдельному указанию.

## Что должно быть в PR

- Проблема и итоговое поведение.
- Основные изменения и затронутые контракты.
- Обновлённые документы или причина отсутствия документальных изменений.
- Выполненные проверки и их результаты; отдельно — непроведённые проверки.
- Миграции, настройки, ограничения и связанные PR, если они есть.

Шаблон: [.github/pull_request_template.md](../.github/pull_request_template.md).

## Проверки перед коммитом и PR

Для задачи, меняющей Prisma schema, данные или работу с БД, пройти следующий порядок до итогового коммита и публикации PR:

1. Проверить целевое подключение без вывода паролей: локальная рабочая БД и тестовая microfronts_test должны быть разными. При необходимости запустить локальную PostgreSQL через npm run db:up, тестовую — npm run db:test:up.
2. Подготовить новую SQL-миграцию для изменений prisma/schema.prisma и проверить её содержание. Не редактировать применённые миграции и не использовать reset/db push вместо миграции для рабочей БД. При переносе каталога сохранить необходимые ID и существующие данные; начальные данные добавлять явно миграцией или штатным seed.
3. Выполнить npm run db:generate для генерации Prisma Client по новой схеме. Генерация клиента сама по себе не обновляет БД.
4. Применить миграции к изолированной тестовой БД и проверить изменение схемы/данных. Штатные npm test и npm run test:e2e через scripts/test-db.mjs выполняют генерацию клиента и migrate deploy для microfronts_test. Выполнять эти наборы последовательно.
5. Выполнить npm run build и относящиеся к задаче тесты, включая API и сохранение существующих сценариев при изменении контрактов. Для товаров проверить чтение из БД, цены корзины, новые поля и даты, ограничения и отсутствие потери существующих данных. Исправить ошибки до завершения задачи.
6. После успешных проверок применить миграцию к локальной рабочей БД через npm run db:deploy и проверить npm run db:status. Не очищать существующую БД; потенциально разрушительные изменения требуют отдельного согласования. Облачную/production БД не обновлять автоматически в рамках локальной проверки.
7. Перезапустить локальный backend при необходимости и проверить затронутый API на обновлённой БД. Подтвердить наличие ожидаемых таблиц/полей/начальных данных и фактический результат сценария.
8. Обновить docs/ и README: модель данных, API, миграции, начальные данные и команды запуска. Проверить итоговый diff и git diff --check. Только после этого делать итоговый commit, push и PR с результатами проверок.

Для изменений кода без изменения БД выполнить сборку и относящиеся к задаче тесты; не создавать пустую миграцию. Для изменений только Markdown проверить ссылки, содержание, UTF-8 и git diff --check; генерация клиента, миграция, сборка и тесты приложения не требуются.

Если обязательная проверка не выполнена или упала, явно указать блокер и не объявлять задачу готовой. Создание PR не означает слияние или закрытие ветки: merge и удаление ветки выполнять только по отдельному указанию пользователя.

Подготовка БД описана в [руководстве](DATABASE_GUIDE.md).

Если доступ к GitHub или инструментам отсутствует, сохранить описание PR, сообщить блокер и не считать задачу опубликованной.
