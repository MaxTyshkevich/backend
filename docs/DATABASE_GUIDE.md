# PostgreSQL: локальный Docker и деплой на Railway

Актуально после перехода backend на PostgreSQL, 22.09.2026. Старые данные SQLite не импортируются: согласован старт с пустой БД. Старые файлы данных не удаляются. Конфигурация Railway подготовлена в коде; изменение облачного проекта и публикация ещё не выполнялись.

## 1. Как связаны части

```text
Локально:
браузер → frontend → Nest на компьютере → localhost:5432 → PostgreSQL в Docker
                                                              ↓
                                       Docker volume postgres-data (данные)

На Railway:
frontend → backend-сервис → внутренняя сеть Railway → PostgreSQL-сервис
                                                           ↓
                                                       его volume
```

**Образ** — установочный шаблон PostgreSQL. **Контейнер** — запущенная программа из образа. **Volume** — отдельный диск с таблицами, записями и настройками пользователей БД. **Prisma** — библиотека, через которую Nest делает запросы, и CLI для изменения схемы. Docker не заменяет Prisma: они решают разные задачи.

Локальная и облачная базы независимы. Таблицы между ними синхронизируют миграции из Git; пользователей и корзины Git не переносит.

## 2. Запуск на этом компьютере

Установлены Node 24 и Docker Desktop. Docker Desktop должен быть запущен в режиме Linux containers. Открой терминал:

```powershell
cd F:\microfronts\backend
npm ci
npm run db:setup
npm run db:up
npm run db:deploy
npm run db:seed
npm run start:dev
```

Что происходит:

1. `npm ci` устанавливает версии библиотек из lockfile.
2. `db:setup` создаёт `.env` со случайным паролем. Уже настроенный файл сохраняется; пароль не выводится в терминал.
3. `db:up` скачивает образ при первом запуске, запускает БД и ждёт готовности.
4. `db:deploy` создаёт структуру таблиц из сохранённых миграций. Демонстрационные данные в миграции не входят.
5. `db:seed` явно заполняет категории и товары; повторный запуск сохраняет существующие записи.
6. `start:dev` генерирует Prisma Client и запускает Nest с перезапуском при изменении кода.

На этом компьютере `.env`, контейнер и таблицы уже настроены. При обычной работе достаточно `npm run db:up`, затем `npm run start:dev`. После получения новых миграций из Git дополнительно выполни `npm run db:deploy`.

Открой [проверку API](http://localhost:3000/api/health). Ответ должен содержать `storage: "postgresql"`. Этот маршрут выполняет запрос к БД, а не только возвращает статическую строку.

Для всего локального стенда вместо отдельного Nest:

```powershell
cd F:\microfronts
npm --prefix backend run db:up
npm --prefix backend run db:deploy
npm --prefix backend run db:seed
npm --prefix ../microfronts-support/integration run dev
```

Не запускай одновременно два экземпляра Nest на одном порту. Для остановки Nest — `Ctrl+C`. Для остановки БД — `npm run db:stop` из backend. Данные останутся. `npm run db:logs` покажет журнал, `docker compose ps` — состояние контейнеров.

Если Docker сообщает `port is already allocated`, поменяй `POSTGRES_PORT` в `.env`, например на `5433`, и тот же порт в `DATABASE_URL`, затем повтори `db:up`. Если изменены `.env` или пароль, перезапусти Nest: изменение env не гарантирует автоматический перезапуск watch-режима.

## 3. Где пароль и как он передаётся

В `.env` есть две связанные настройки:

```dotenv
POSTGRES_PASSWORD=твой_локальный_пароль
DATABASE_URL=postgresql://microfronts:твой_локальный_пароль@localhost:5432/microfronts?schema=public
```

Это пояснение формата, а не реальные значения. Скрипт генерирует пароль из шестнадцатеричных символов, чтобы его можно было безопасно включить в URL. Если задаёшь пароль вручную, специальные символы в части пароля `DATABASE_URL` нужно URL-кодировать; значение `POSTGRES_PASSWORD` остаётся обычным паролем. Например, `@` в URL записывается как `%40`.

`POSTGRES_PASSWORD` получает PostgreSQL при первоначальном создании БД. `DATABASE_URL` получает Nest/Prisma, чтобы подключаться к этой БД. В строке последовательно записаны протокол, имя пользователя, пароль, адрес, порт и имя базы. Пароль PostgreSQL не является паролем пользователя сайта: пароли сайта хранятся отдельно как scrypt-хеши в `users`.

`.env` и его резервные копии исключены из Git и Docker-образа. `.env.example` содержит только пример. Не помещай URL базы в `VITE_*`: такие значения могут попасть в браузер. Env, уже переданные процессу, имеют приоритет над `.env`; при неожиданном подключении проверь, не остался ли в терминале старый `DATABASE_URL`.

Если в старом `.env` была другая настройка БД, есть явная команда `npm run db:setup -- --configure-local`: она сохраняет копию `.env.before-postgres-*` и настраивает новую локальную строку. **Она не меняет пароль существующей БД**. Использовать её вместо смены пароля нельзя: новый пароль в файле и старый в volume перестанут совпадать.

## 4. Удаление контейнера и смена пароля

| Действие | Данные | Пароль внутри PostgreSQL |
| --- | --- | --- |
| Остановить / перезапустить контейнер | Остаются | Прежний |
| Удалить контейнер, затем `db:up` с тем же volume | Остаются | Прежний |
| Поменять только `.env` | Остаются | Прежний; Nest получит ошибку авторизации |
| Сменить пароль командой PostgreSQL и обновить `.env` | Остаются | Новый |
| Удалить **volume** и создать БД заново | Все данные удалены | Берётся из env при новой инициализации |

Здесь volume называется `microfronts-backend_postgres-data`; его видно в Docker Desktop → Volumes. `npm run db:down` удаляет контейнеры и сеть, но сохраняет volume. `docker compose down -v` удаляет также данные; для обычной работы эта команда не нужна. Не меняй имя Compose-проекта/volume без причины: иначе Docker может создать другую пустую базу.

Чтобы сменить пароль **без удаления данных**, останови Nest и открой SQL-консоль:

```powershell
docker compose exec db psql -U microfronts -d microfronts
```

Внутри консоли:

```text
\password microfronts
```

Введи новый пароль дважды по запросу, затем `\q` для выхода. Такой ввод не записывает пароль в историю SQL-команд. Обнови `POSTGRES_PASSWORD` и пароль в `DATABASE_URL` файла `.env`, запусти `npm run db:up`, `npm run db:status`, затем Nest. Никакого удаления контейнера для смены пароля не требуется. Механизм первоначальной инициализации описан в [документации официального образа](https://hub.docker.com/_/postgres).

## 5. Структура backend и схема

Профили (`profiles`, связь 1:1 с пользователем), комментарии (`comments`, связи с товаром и автором), их API и отдельное локальное demo-заполнение описаны в [руководстве профилей и комментариев](PROFILE_COMMENTS_API.md). Каталог seed расширен до 30 товаров; прежние ID сохранены.

```text
src/
  app.module.ts           сборка модулей приложения
  main.ts                 запуск HTTP-сервера
  auth/                   регистрация, вход, сессии, auth controller
  cart/                   корзины и атомарный перенос гостевой корзины
  catalog/                чтение товаров/категорий и HTTP API каталога
  shop/                   HTTP-маршруты товаров/корзин и проверка БД
  database/               общий PrismaService и DatabaseModule
  common/guards/          CSRF-защита
  generated/prisma/       генерируемый клиент, не редактировать вручную
prisma/
  schema.prisma           описание моделей
  migrations/             SQL-история изменений
scripts/                  настройка окружения и запуск тестов
```

`CartModule` экспортирует сервис, который используют авторизация и HTTP-модуль магазина. Это позволяет не создавать циклическую зависимость между контроллерами авторизации и корзины. Старый SQLite-сервис заменён; копия его незакоммиченного содержимого сохранена локально в `.temp/database.service.before-postgres.ts`.

| Модель Prisma / таблица | Что хранит |
| --- | --- |
| `Product` / `products` | Товары, описание, цена в минимальных единицах, рейтинг, даты, categoryId |
| `Category` / `categories` | Категории с уникальным slug |
| `User` / `users` | UUID пользователя, уникальный email, имя, хеш пароля |
| `Session` / `sessions` | Хеш токена, ссылку на пользователя, срок сессии |
| `Cart` / `carts` | Ключ гостя либо `user:<uuid>`, количества товаров в JSONB, ревизию |
| `GuestClaim` / `guest_claims` | Факт однократного переноса гостевой корзины |
| `AuthAttempt` / `auth_attempts` | Счётчики и сроки ограничения попыток входа |

Пользователь связан с сессиями и отметками переноса. Каталог хранится в PostgreSQL. Миграции создают структуру; `npm run db:seed` отдельно добавляет демонстрационные категории и товары. `Product.categoryId` обязателен, по умолчанию `other`; перед созданием товара с этим значением категория other должна существовать. Удаление используемой категории запрещено. Seed сначала создаёт категории, затем keyboard/dock в peripherals и monitor в monitors, сохраняя уже существующие записи. Категории и связи можно редактировать через Prisma Studio. Корзина сохраняет прежний HTTP-контракт; одновременные изменения корзин защищены транзакциями и блокировками по ключу.

Чтобы увидеть таблицы через интерфейс:

```powershell
npm run db:studio
```

Открой локальный адрес, напечатанный Prisma Studio. Зарегистрируй тестового пользователя через приложение, добавь товар, затем посмотри `User`, `Session`, `Cart`. Studio умеет менять реальные записи подключённой БД — для обучения используй локальную базу. При закрытии Studio данные сохраняются.

## 6. Как менять схему

Обязательное правило из [AGENTS.md](../AGENTS.md#база-данных-и-проверки): SQL-миграцию генерирует Prisma на основании изменений `schema.prisma`. Не создавать `migration.sql` вручную и не заменять сгенерированный SQL самостоятельно написанным. Сначала выполнить генерацию с `--create-only`, затем просмотреть и проверить SQL перед применением. Если Prisma не генерирует нужное изменение (например, заполнение существующих данных или отдельное ограничение), обсудить решение с пользователем до ручных правок. Недоступность БД или ошибка генерации не разрешает писать миграцию вручную.

Пример: добавить необязательное поле `createdAt` модели `User`:

```prisma
createdAt DateTime? @map("created_at") @db.Timestamptz(3)
```

Далее **локально**:

```powershell
npm run db:migrate -- --name add_user_created_at --create-only
# Открой новый prisma/migrations/.../migration.sql и проверь SQL.
npm run db:migrate
npm run db:generate
npm run build
```

Это учебный пример, поле сейчас не добавлено. В Git входят схема, миграция и lockfile при изменении зависимостей; данные и сгенерированный клиент не входят. На Railway команда `db:deploy` применит именно сохранённый SQL. Создание миграций (`migrate dev`) и применение готовых (`migrate deploy`) — разные действия. В Prisma 7 клиент генерируется явно; seed запускается явно отдельной командой `npm run db:seed`, настроенной в prisma.config.ts. См. [Prisma CLI](https://docs.prisma.io/docs/orm/reference/prisma-cli-reference).

Не редактируй уже применённые общие миграции и не используй `migrate reset` на нужных данных. Для обязательного нового поля сначала добавляют nullable-поле, заполняют старые записи, потом вводят `NOT NULL`. Миграции не заменяют бэкап и не обеспечивают автоматический откат удалённых данных.

### Пересоздание разрешённой локальной БД

Если локальные данные больше не нужны и сброс явно согласован, проверьте адрес подключения (локальный Docker, база microfronts), затем выполните `npx prisma migrate reset`. Команда удаляет все данные и историю применения в выбранной схеме и применяет миграции заново. После неё выполните `npm run db:generate` и `npm run db:seed`. Удалять Docker volume для этого не требуется. В Prisma 7 seed выполняется отдельно. Пользователей seed не создаёт: после сброса нужно зарегистрироваться заново.

Если в БД уже применены прежние версии миграций товаров/категорий, их контрольные суммы будут отличаться. Для разрешённого одноразового локального контура нужен согласованный reset; для любой другой БД требуется отдельный план перехода. Не исправляйте контрольные суммы вручную и не переносите команду сброса в облачное окружение. Правило неизменности применённых общих миграций сохраняется.

## 7. Railway: что нужно сделать в существующем проекте

`render.yaml` удалён из backend: это конфигурация другого провайдера. Вместо него добавлен [railway.json](../railway.json). Он задаёт сборку Dockerfile, миграции перед запуском, старт API и healthcheck. Другие приложения и их конфиги Render не менялись.

1. Открой Railway-проект, где уже размещён backend, и нужное окружение. Добавь сервис **PostgreSQL** через меню New/Database. Дождись его готовности и проверь, что к нему подключён постоянный volume. Создание сервиса может изменить расходы проекта.
2. В Variables **backend-сервиса** добавь reference variable `DATABASE_URL`, выбрав переменную `DATABASE_URL` PostgreSQL-сервиса. Если сервис называется `Postgres`, запись имеет вид `${{Postgres.DATABASE_URL}}`. Используй фактическое имя сервиса. Локальный `.env` туда не загружай.
3. Сохрани `NODE_ENV=production`, актуальные `CORS_ORIGINS` и настройку frontend proxy. `APP_DB_PATH` больше не используется. Не устанавливай `COOKIE_SECURE=false` на публичном HTTPS. Локальные `POSTGRES_PASSWORD`/`POSTGRES_PORT` backend-сервису Railway не нужны.
4. Для отдельного backend-репозитория root directory — его корень. В интерфейсе проверь, что Railway обнаружил именно этот `railway.json` и Dockerfile.
5. До релиза проверь итоговые Settings: builder Dockerfile, pre-deploy `npm run db:deploy`, start `node dist/main.js`, healthcheck `/api/health`. Эти значения уже есть в файле. Убери конфликтующие старые команды в UI. Дай БД завершить первый запуск до первого релиза API.
6. После сохранения настроек и публикации кода дождись успешного pre-deploy, затем успешного запуска API. Проверь `/api/health`, регистрацию, вход и корзину. Старые SQLite-пользователи здесь отсутствуют по принятому решению.

На новой облачной БД демонстрационное заполнение при необходимости выполняется отдельно командой `npm run db:seed` после миграций. Скрипт включён в Docker-образ. Автоматический seed в pre-deploy не добавлен.

Railway предоставляет переменные подключения сервиса; внутренняя строка предназначена для сервисов того же проекта/окружения. Публичный адрес нужен только для разрешённого доступа извне, а не для связи backend с соседней БД. См. [PostgreSQL на Railway](https://docs.railway.com/databases/postgresql).

Миграции выполняются после сборки в отдельном pre-deploy контейнере с доступом к env и приватной сети. При ошибке миграции релиз останавливается. Prisma CLI намеренно оставлен в production dependencies и Docker-образе, чтобы этот шаг мог работать. На этапе `docker build` подключения к БД нет. См. [pre-deploy Railway](https://docs.railway.com/deployments/pre-deploy-command).

При redeploy API PostgreSQL продолжает жить отдельным сервисом. Обновление образа БД в пределах одной major-версии и переход на новую major-версию — разные процедуры; второе требует отдельного плана обновления. Локально закреплена major-версия 17; при создании облачной БД предпочтительно выбрать ту же и проверить фактическую версию Railway.

На Railway смена env сама по себе тоже не гарантирует смену пароля существующей PostgreSQL. Сначала меняют пароль роли в БД через поддерживаемый платформой процесс/SQL, затем согласованно обновляют переменные БД и ссылку backend, перезапускают подключения. Не удаляй PostgreSQL-сервис или volume ради смены пароля.

## 8. Резервные копии

Для локальной БД из backend:

```powershell
New-Item -ItemType Directory -Force backups | Out-Null
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
docker compose exec -T db pg_dump -U microfronts -d microfronts -Fc -f /tmp/microfronts.dump
# Следующий шаг только если pg_dump завершился успешно.
docker compose cp db:/tmp/microfronts.dump "./backups/microfronts-$stamp.dump"
```

`backups` исключён из Git. Скопируй архив на другой диск/в защищённое хранилище. Для репетиции восстановления, не трогая рабочую БД:

```powershell
$restoreDb = "microfronts_restore_$(Get-Date -Format 'yyyyMMddHHmmss')"
docker compose exec -T db createdb -U microfronts $restoreDb
docker compose cp "./backups/microfronts-$stamp.dump" db:/tmp/restore.dump
docker compose exec -T db pg_restore -U microfronts -d $restoreDb --no-owner --no-privileges --exit-on-error /tmp/restore.dump
```

Проверяй код завершения каждого шага и данные восстановленной БД; не продолжай после ошибки. Это логический backup одной БД, не резервная копия глобальных ролей сервера. См. [pg_dump/восстановление](https://www.postgresql.org/docs/17/backup-dump.html).

На Railway включи расписание в **Backups** у volume PostgreSQL, сделай ручной backup перед опасными миграциями и проверь восстановление в отдельную базу. Расписание и доступность зависят от настроек аккаунта; в этой работе они не включались. См. [резервные копии Railway](https://docs.railway.com/volumes/backups).

## 9. Тесты и полный Docker-стенд

```powershell
# Из backend:
npm run db:test:up
npm test
npm run test:e2e
npm run build
```

Тесты используют отдельный PostgreSQL на `127.0.0.1:5434`, БД `microfronts_test`. Его данные временные. Runner отказывается очищать dev/production URL, после применения миграций явно запускает seed каталога. При другом порте задай `POSTGRES_TEST_PORT` в `.env`; для внешнего тестового запуска доступен `TEST_DATABASE_URL`, разрешён только локальный тестовый сервер с указанным именем БД. Не запускай одновременно несколько наборов тестов против одной test-БД.

API- и браузерные тесты integration тоже используют этот контейнер, автоматически применяют миграции и очищают только test-БД перед стартом API. Перед ними нужна сборка backend. Например, `npm --prefix ../microfronts-support/integration run test:api` из workspace.

Полный Docker-стенд, включая frontend, использует **другую локальную БД** с отдельным volume проекта integration:

```powershell
cd F:\microfronts-support\integration
docker compose --env-file ../../microfronts/backend/.env up --build -d
```

Shell доступен на `http://localhost:8080`. Compose ждёт готовности `db`, затем успешной миграции `migrate`, затем API. Внутри этой сети адрес БД — `db:5432`. Используемый здесь пароль должен быть URL-безопасным, как пароль из `db:setup`, поскольку Compose подставляет его в URL без кодирования.

Для повторного релиза полного стенда: собрать образы, явно выполнить `docker compose --env-file ../../microfronts/backend/.env run --rm migrate`, и только при успехе обновлять backend/frontend. Завершённый старый migration-контейнер не должен заменять проверку нового релиза.
