# Базы данных, Docker и миграции Prisma

> Исторический отчёт до внедрения. С 22.09.2026 PostgreSQL/Prisma подключены; актуальные команды и Railway описаны в [DATABASE_GUIDE.md](DATABASE_GUIDE.md). Упоминания SQLite и Render ниже относятся к прежнему состоянию.

Дата: 21 сентября 2026 года. Отчёт по текущему коду `apps/backend` и конфигурации `integration/compose.yaml`.

## Рекомендация

Поднимать PostgreSQL в отдельном Docker-контейнере для разработки и CI — разумный следующий шаг. Для ежедневной работы удобнее оставить Nest на хосте с hot reload, а в Docker запускать только PostgreSQL. Для интеграционных проверок — весь стенд в Compose. Для production можно выбрать управляемый PostgreSQL либо контейнер на собственном сервере, если есть готовность обслуживать данные самостоятельно.

Однако сейчас рабочая БД проекта — **SQLite**, а Prisma с PostgreSQL пока не подключены к API. Поэтому добавление контейнера PostgreSQL само по себе ничего не изменит: необходимо перенести слой хранения и отдельно решить судьбу существующих данных. Микрофронтенды не требуют отдельных БД: текущему единому backend достаточно одной PostgreSQL с несколькими таблицами.

Это проектное предложение. В рамках отчёта контейнеры не запускались, миграции не применялись, зависимости и приложение не менялись.

Сейчас схема создаётся через `CREATE TABLE IF NOT EXISTS`, после чего безусловно выставляется `PRAGMA user_version = 1`. Это начальная инициализация, а не последовательность версионированных миграций: добавленное в код поле не появится автоматически в существующей таблице.

В [README backend](../README.md) SQLite описана правильно. Текущий `render.yaml` (удалён при переходе на Railway) задаёт `starter` и persistent disk. При обновлении инструкции следует ориентироваться на исходники и конфигурацию; фактический облачный deploy этим исследованием не проверялся.

## 2. Варианты реализации

| Вариант | Как работает | Плюсы | Ограничения / когда выбирать |
| --- | --- | --- | --- |
| A. Сохранить SQLite в контейнере API | Текущий Compose и постоянный volume | Минимум изменений и инфраструктуры | Подходит небольшому стенду с одним API; нужно добавить миграции SQLite и бэкапы |
| B. PostgreSQL в Docker, Nest на хосте | БД доступна через `127.0.0.1`, Nest запускается `start:dev` | Удобная отладка; одинаковая версия БД у команды | Требуется переход сервисов на PostgreSQL/Prisma; рекомендовано для разработки |
| C. PostgreSQL, миграции и API в Compose | Отдельные сервисы `db`, `migrate`, `backend` | Воспроизводимый интеграционный стенд | Нужно обновить Dockerfile и порядок старта; для изменения API нужна пересборка либо dev-конфигурация |
| D. API в контейнере, управляемый PostgreSQL | БД обслуживает провайдер | Меньше эксплуатационных задач | Стоимость, сеть и ограничения провайдера; backup/PITR зависят от выбранного сервиса |
| E. PostgreSQL в Docker на своём сервере | Собственный диск, мониторинг, резервное копирование | Контроль над окружением | Команда отвечает за восстановление, обновления, доступность и свободное место |

SQLite — встроенная библиотека, а не сетевой сервер. Выносить её файл в отдельный «контейнер БД» без нового сетевого сервиса не даёт пользы. Для текущего варианта A достаточно существующего volume. Общий файл SQLite не следует превращать в способ масштабирования нескольких API по разным хостам.

Docker упрощает установку и воспроизводимость, но сам по себе не обеспечивает резервное копирование или отказоустойчивость. Один PostgreSQL-контейнер на одном сервере остаётся одной точкой отказа. Redis сейчас не требуется; добавлять его стоит под конкретную задачу, например распределённый rate limiting.

## 3. Пример PostgreSQL для локальной разработки

Ниже **предлагаемый**, пока не созданный файл `apps/backend/compose.db.yaml`. Это самостоятельный пример для варианта B. PostgreSQL 17 выбран как конкретная major-версия, а не как заявление о самой новой версии. Для воспроизводимого CI следует закрепить проверенный patch-тег или digest.

```yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_DB: microfronts
      POSTGRES_USER: microfronts
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?Set POSTGRES_PASSWORD}
    ports:
      - "127.0.0.1:5432:5432"
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U microfronts -d microfronts"]
      interval: 5s
      timeout: 3s
      retries: 20
    restart: unless-stopped

volumes:
  postgres-data:
```

После создания файла из каталога `apps/backend`:

```powershell
# Только пример локального пароля; реальные секреты не коммитить.
$env:POSTGRES_PASSWORD = 'local-dev-only-change-me'
docker compose -f compose.db.yaml up -d --wait db
$env:DATABASE_URL = 'postgresql://microfronts:local-dev-only-change-me@localhost:5432/microfronts?schema=public'
```

Эти команды поднимут БД, но **текущий API продолжит работать с SQLite**, пока не реализован переход из раздела 4. При занятом порте можно публиковать `127.0.0.1:5433:5432` и использовать `localhost:5433` с хоста.

Внутри Compose API обращается к `db:5432`, а не к `localhost`. При полностью контейнерном стенде публиковать порт БД на хост необязательно. Пароль в URL необходимо URL-кодировать, если он содержит специальные символы.

Пользователь, созданный через `POSTGRES_USER`, имеет повышенные права: это упрощение только для локального стенда. В production нужны отдельные роли для приложения и миграций. Переменные и init-скрипты образа действуют при первоначальном создании пустого data directory; смена env не меняет пароль существующей БД. Для PostgreSQL 18+ официальный образ изменил организацию `PGDATA` и рекомендуемую точку монтирования: пример для 17 нельзя переносить механически. См. [официальный образ PostgreSQL](https://hub.docker.com/_/postgres).

Обычный `docker compose down` сохраняет named volumes. Флаг `-v` удаляет их и данные; это не штатная команда остановки рабочего стенда. Смена major-версии PostgreSQL требует процедуры обновления, например dump/restore, а не простой замены тега поверх старого volume.

## 4. Что потребуется изменить в Nest и Prisma

1. Описать реальные сущности: пользователь, сессия, корзина, отметка переноса гостевой корзины, попытки входа. Товары можно пока оставить в коде. Если переносить их в БД, добавить модель товара и начальное наполнение отдельной задачей.
2. Сохранить существующие идентификаторы. Пользователи имеют строковые UUID; ключ корзины бывает UUID гостя или строкой `user:<uuid>`, поэтому текущий `carts.id` нельзя просто сделать PostgreSQL UUID. Учебный `User.id Int` из Prisma не подходит.
3. Выбрать представление корзины. JSONB ближе к текущему `quantities` и упрощает первый перенос. Таблица `CartItem` с уникальной парой `(cartId, productId)` удобнее для ограничений и отдельных обновлений, но увеличивает объём работ. Для первого этапа рекомендую сохранить структуру, а нормализацию сделать отдельно при необходимости.
4. Подключить PostgreSQL driver adapter Prisma 7, например `@prisma/adapter-pg` и `pg`, согласовать версии Prisma-пакетов и lockfile. Создать Nest-провайдер PrismaClient с управлением жизненным циклом подключения.
5. Перевести сервисы и вызывающие их контроллеры на асинхронный доступ. Проверки пользователя и выбор ключа корзины тоже должны ожидать запросы. Нельзя передать async-функцию существующему `transaction()`: его синхронный `COMMIT` выполнится до завершения Promise.
6. Сохранить атомарность переноса гостевой корзины, обеспечить защиту от потери параллельных изменений корзины и атомарное ограничение попыток входа. Одного `$transaction` с чтением и записью недостаточно без выбранной стратегии конкуренции: блокировка строки, проверка `revision` с повтором либо Serializable с обработкой конфликтов. Нужны тесты одновременных запросов.
7. Добавить индексы по внешним ключам и срокам истечения там, где это оправдывают запросы; сохранить уникальность email и отметки переноса гостевой корзины.
8. Настроить CLI отдельно от Nest: `ConfigModule.forRoot()` не запускается при `prisma migrate`. Передавать env из процесса/CI либо явно загружать `.env` через `import 'dotenv/config'` с объявленной зависимостью.
9. Согласовать `moduleFormat` Prisma с фактической сборкой Nest. Сейчас генератор задаёт ESM, а `package.json` не содержит `type: module`; проверить сгенерированные импорты сборкой и запуском готового контейнера.

Особенности адаптеров, env и генерации подтверждаются [руководством перехода на Prisma 7](https://docs.prisma.io/docs/orm/v6/more/upgrades/to-v7). Это список необходимых изменений, а не утверждение, что текущая сборка уже сломана: Prisma Client сейчас не используется.

## 5. Как работают миграции Prisma

Миграция — сохранённый SQL-переход между версиями структуры БД. `schema.prisma` описывает желаемую модель, `prisma/migrations/<timestamp>_<name>/migration.sql` — конкретные изменения. В самой БД Prisma ведёт таблицу `_prisma_migrations`, включая имена, контрольные суммы и сведения об исполнении. Историю миграций и `migration_lock.toml` хранят в Git рядом со схемой. Успешно применённые общие миграции не переписывают: создают следующие. См. [историю миграций Prisma](https://docs.prisma.io/docs/orm/v7/prisma-migrate/understanding-prisma-migrate/migration-histories).

### Разработка

После подключения реальных моделей и отдельной dev-БД, из `apps/backend`:

```powershell
npx prisma validate
npx prisma migrate dev --name init_shop --create-only
# Проверить созданный migration.sql, исправить опасные преобразования.
npx prisma migrate dev
npx prisma generate
# Только после настройки migrations.seed и написания seed-скрипта:
npx prisma db seed
```

Для следующих изменений использовать смысловые имена, например `add_session_expiry_index`. Сначала ревью SQL, затем применение к dev-БД и тесты. Prisma 7 требует явно запускать генерацию клиента и seed. `db push` меняет структуру без полноценной истории миграций и не подходит как основной процесс релиза. `migrate reset` уничтожает данные и допустим только на предназначенной для этого dev/test-БД. См. [справочник Prisma CLI](https://docs.prisma.io/docs/orm/reference/prisma-cli-reference).

`migrate dev` использует временную shadow database для воспроизведения истории и проверки расхождений схемы. Локально можно разрешить создание БД или выделить отдельную shadow-БД. Её адрес никогда не должен совпадать с рабочей БД; она может очищаться. Для production-команды `migrate deploy` shadow-БД не нужна. См. [shadow database](https://docs.prisma.io/docs/orm/prisma-migrate/understanding-prisma-migrate/shadow-database).

### CI и production

На сборке установить зависимости через lockfile, выполнить `prisma generate` и собрать Nest. Затем отдельным release job с доступом к целевой БД:

```powershell
npx prisma migrate deploy
npx prisma migrate status
```

`deploy` применяет подготовленные SQL-файлы, а не создаёт миграции из схемы. Он не проверяет весь schema drift и не генерирует клиент. `status` также не заменяет сравнение реальной структуры с ожидаемой. Эти свойства описаны в [архитектуре Prisma Migrate](https://github.com/prisma/prisma-engines/blob/main/schema-engine/ARCHITECTURE.md).

Рекомендуемый pipeline проекта: временный PostgreSQL → применение всей истории с нуля → API-тесты → проверка обновления БД предыдущего релиза с данными → сборка образов → backup целевого окружения → release job миграций → запуск новой версии API → smoke-проверка регистрации, входа и корзины. Production seed с тестовыми аккаунтами сюда не включать.

### Порядок старта в Docker

Для варианта C предлагается цепочка:

```text
db (healthcheck прошёл)
  → migrate (prisma migrate deploy завершился с кодом 0)
    → backend (готовность API и запрос к БД)
      → frontend
```

В Compose это выражается через `depends_on` с `service_healthy` и `service_completed_successfully`. Это ожидание при запуске, а не механизм восстановления соединения после последующего падения БД. Приложению всё равно нужны обработка ошибок подключения и корректный readiness. См. [порядок запуска Compose](https://docs.docker.com/compose/how-tos/startup-order/).

Текущий Dockerfile не копирует `prisma` и `prisma.config.ts`, не генерирует клиент и удаляет CLI через `npm prune --omit=dev`. Поэтому сервис `migrate` на текущем runtime-образе не готов к работе. Предлагается отдельная стадия/образ миграций с CLI, схемой, конфигом и SQL-историей; runtime API содержит клиент и драйвер, но не обязан содержать CLI. Генерацию клиента выполнять до `nest build`. Для CLI-конфига, требующего `DATABASE_URL` даже при генерации, передавать синтаксически корректный build-only URL без реальных секретов; генерация не должна требовать доступа к production.

В production запускать один явно выделенный migration job на релиз. Для повторного релиза в Compose job должен запускаться заново на новом образе, а не считаться выполненным по старому завершённому контейнеру.

## 6. Перенос SQLite → PostgreSQL и изменения без потери данных

Prisma Migrate переносит структуру в рамках выбранного провайдера; он не копирует автоматически данные SQLite в PostgreSQL. Для этого проекта нужны начальная PostgreSQL-миграция и отдельный проверяемый импорт.

Если данные одноразовые, после явного решения владельца можно начать с пустой PostgreSQL. Если данные нужно сохранить, рекомендую для этого небольшого стенда короткое окно обслуживания:

1. Отрепетировать импорт на копии SQLite и новой PostgreSQL.
2. Остановить запись в старую БД, сделать согласованный backup и зафиксировать момент переключения.
3. Применить PostgreSQL-миграции и импортировать записи с сохранением ID, password hash и связей. Миллисекунды `expires_at`/`resets_at` явно преобразовать в выбранный тип времени; JSON корзин проверить на корректность.
4. Перенести `guest_claims`, чтобы гостевая корзина не присоединилась повторно. Для сессий выбрать сохранение хешей токенов и сроков либо принудительный повторный вход; это продуктовое решение, а не скрытый побочный эффект.
5. Сверить количество записей, внешние ключи, содержимое корзин и контрольные выборки, проверить вход существующего пользователя. Переключить API только после проверки.
6. Сохранить старую SQLite неизменной на согласованный срок. Если PostgreSQL уже принял новые записи, простой возврат к SQLite потеряет эти изменения: для отката понадобится их перенос либо согласованное восстановление на определённый момент.

Если Prisma вводится поверх **уже существующей PostgreSQL**, используют baselining: фиксируют исходную структуру как начальную миграцию, проверяют соответствие реальной БД и отмечают baseline применённым через `migrate resolve --applied`. SQL создания существующих таблиц повторно не запускается. Это не способ переноса между SQLite и PostgreSQL. См. [baselining](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/baselining).

Для дальнейших изменений применять подход expand → backfill → contract. Например, новое обязательное поле сначала сделать nullable, выпустить совместимый код, заполнить старые записи отдельным повторяемым скриптом, проверить отсутствие пропусков и только затем добавить `NOT NULL`. Backfill — заполнение существующих данных; он отличается от backlog — списка задач. Длинные преобразования лучше выполнять порциями с прогрессом и возможностью продолжения.

Prisma не создаёт универсальные down-миграции. Обычно откатывают код, если схема совместима, либо выпускают новую исправляющую миграцию. После сбоя нужно проверить фактическое состояние и частично выполненный SQL. `migrate resolve --rolled-back` меняет запись истории, но не отменяет SQL; `--applied` не выполняет недостающий SQL. Их используют только после устранения причины и согласования истории с реальностью. См. [устранение сбоев миграций](https://www.prisma.io/docs/orm/prisma-migrate/workflows/patching-and-hotfixing).

## 7. Бэкапы и восстановление

Бэклог, журнал миграций и бэкап — разные вещи. На случай, если под «бэклогами» подразумевались резервные копии, здесь приведён отдельный процесс. Docker volume сохраняет данные между пересозданиями контейнера, но не защищает от удаления, ошибки SQL или потери диска. Prisma Migrate не является инструментом резервного копирования.

### Текущая SQLite

Включён WAL, поэтому простое копирование только `shop.sqlite` у работающего приложения может пропустить актуальные изменения. Использовать SQLite Online Backup API либо `VACUUM INTO`, получая согласованную копию; затем переносить результат за пределы сервера. Проверять восстановление на отдельной копии и выполнять проверку целостности. См. [официальные способы backup SQLite](https://www.sqlite.org/backup.html).

### Предлагаемый PostgreSQL

Для небольшого стенда подойдёт логический backup `pg_dump` в custom format с восстановлением через `pg_restore`. Команды ниже предназначены для **предлагаемого** `compose.db.yaml`, выполняются из `apps/backend`; роль и БД соответствуют его локальному примеру:

```powershell
New-Item -ItemType Directory -Force backups | Out-Null
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
docker compose -f compose.db.yaml exec -T db pg_dump -U microfronts -d microfronts -Fc -f /tmp/microfronts.dump
# Продолжать только после успешного завершения pg_dump.
docker compose -f compose.db.yaml cp db:/tmp/microfronts.dump "./backups/microfronts-$stamp.dump"

# Репетиция восстановления в НОВОЙ, ещё не существующей БД.
$restoreDb = "microfronts_restore_$(Get-Date -Format 'yyyyMMddHHmmss')"
docker compose -f compose.db.yaml cp "./backups/microfronts-$stamp.dump" db:/tmp/restore.dump
docker compose -f compose.db.yaml exec -T db createdb -U microfronts $restoreDb
docker compose -f compose.db.yaml exec -T db pg_restore -U microfronts -d $restoreDb --no-owner --no-privileges --exit-on-error /tmp/restore.dump
```

В автоматизации после **каждой** команды проверять код завершения и прекращать процесс при ошибке. Файл передаётся через `docker compose cp`, без перенаправления бинарного dump через PowerShell. Каталог `backups` до использования добавить в `.gitignore`; копии шифровать и отправлять во внешнее хранилище. Восстановление завершено только после проверки данных и запуска API против восстановленной БД.

`pg_dump` сохраняет одну БД; глобальные роли и настройки доступа требуют отдельного воспроизводимого описания или backup. Для восстановления нужны совместимые версии утилит. См. [SQL dump PostgreSQL](https://www.postgresql.org/docs/17/backup-dump.html) и [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html).

Предлагаемая стартовая политика для учебного стенда: ежедневная копия, дополнительная перед переносом/опасной миграцией, хранение 7 ежедневных и 4 еженедельных копий вне сервера, ежемесячная репетиция восстановления. Это предложение, не уже настроенная автоматизация. При одной копии в сутки возможна потеря до суток изменений. Если это неприемлемо, определить меньший RPO (допустимую потерю данных) и использовать более частое копирование либо архивирование WAL/PITR. RTO — допустимое время восстановления — проверить практической репетицией.

| DB-03 | P0 | Описать рабочие модели и начальную миграцию | DB-01 | Миграция поднимает пустую БД; типы ID, ограничения и сроки совместимы с API |
