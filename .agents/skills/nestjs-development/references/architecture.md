# Архитектурные решения для этого backend

Читай разделы по задаче: «Ресурсы и модули» — для структуры; «HTTP и DTO» — для API; «Доступ» — для сессий и прав; «Данные» — для Prisma и конкурентных операций. Это проектные критерии выбора, а не шаблон для массовой переделки существующего кода.

## Ресурсы и модули

Разделяй независимые HTTP-ресурсы по контроллерам. Для товаров используй префикс `@Controller('api/products')`: GET списка, GET по ID и POST создания принадлежат ProductsController. Категории обслуживает CategoriesController с префиксом `api/categories`. Публичные чтения и защищённая запись одного ресурса могут находиться в одном контроллере; Guards назначаются соответствующим обработчикам.

Положение файлов и имя класса сами по себе не меняют URL. При переносе проверь сочетание префикса контроллера, декоратора метода и глобального префикса bootstrap, чтобы сохранить `/api/products`, а не случайно получить `/api/api/products`.

Выбирай размер модуля по связности и зависимостям, а не по количеству таблиц:

| Решение | Когда подходит |
| --- | --- |
| Два контроллера внутри CatalogModule | Товары и категории развиваются как одна область, а зависимости остаются простыми |
| ProductsService и CategoriesService внутри области | Сценарии ресурсов имеют самостоятельную ответственность; не добавляй новые несвязанные обязанности в общий CatalogService |
| Самостоятельные ProductsModule и CategoriesModule | Нужны отдельные границы зависимостей, повторное использование или независимое развитие; CatalogModule может остаться модулем композиции, если это полезно |

Это примеры целевого устройства при согласованном изменении, а не описание уже выполненного рефакторинга. Перед выбором прочитай текущие импорты и потребителей. Если перенос требует существенных изменений вне задачи, предложи отдельный этап.

Сервис предоставляет предметные операции и не требует Express Request/Response как аргументы бизнес-сценария. HTTP-заголовки, cookie и статусы обрабатываются на границе API; бизнес-правила, транзакции и координация операций — в сервисах. NestJS HttpException допустимы в сервисах этого HTTP-приложения; отдельную иерархию доменных ошибок вводи только при реальной необходимости других транспортов или потребителей.

Регистрация провайдера в нескольких модулях может создать несколько экземпляров. Для общего провайдера используй импорт модуля и его exports. При цикле сначала пересмотри владельцев операций; forwardRef не должен маскировать неверное распределение ответственности. Не делай модуль глобальным только ради сокращения imports.

Прямое использование PrismaService в предметном сервисе допустимо. Отдельный repository нужен, когда он скрывает содержательную повторяемую логику доступа к данным или другую реальную вариативность; не создавай интерфейс и обёртку для каждого вызова Prisma. Не дублируй Prisma-модели новыми entity-классами без потребности.

## HTTP и DTO

Для нового изменяющего маршрута зафиксируй источник каждого значения: проверенный пользователь, DTO, параметры URL или серверные значения по умолчанию. Клиент не назначает себе роль, владельца ресурса и служебные поля.

Используй class-validator и class-transformer с фактическими настройками ValidationPipe из bootstrap. Проверяй формат, длину, диапазоны и обязательность полей, включая вложенные объекты, если они есть. Преобразования типов должны быть явными: не превращай произвольную строку в число без проверки. Согласуй смысл отсутствующего поля и null, особенно для PATCH. Не используй DTO Prisma как публичный HTTP-контракт автоматически.

В этом проекте whitelist и forbidNonWhitelisted запрещают неизвестные поля только там, где подключён ValidationPipe и аргумент имеет runtime-класс DTO. Интерфейс, inline-тип и TypeScript cast не обеспечивают такую проверку. E2E bootstrap должен применять те же настройки; Test.createTestingModule не исполняет main.ts.

Явно формируй публичный ответ через select/mapper или подходящий механизм сериализации. Response DTO описывает контракт, но сам по себе не удаляет поля объекта во время выполнения. Не возвращай passwordHash, токен, его хеш или внутреннюю запись сессии. Для дат и nullable-полей сохраняй согласованный JSON-формат.

Сначала определи ожидаемые ошибки, затем отобрази известные ошибки Prisma в них. Для создания товара: 201 — успех, 400 — неверный ввод или недопустимая категория, 409 — занятый уникальный ID. Не превращай любой сбой БД в 400/409 и не возвращай клиенту текст внутренней ошибки. Не копируй эти статусы механически на другие сценарии.

При рефакторинге сохраняй методы, URL, статусы, тело, headers и правила доступа, если изменение контракта не согласовано. Для сохранения совместимости недостаточно переименовать файлы и пройти TypeScript-сборку.

## Доступ: сессия, роль и владелец

В проекте браузер хранит токен в HttpOnly cookie, а сервер проверяет запись сессии, срок действия и актуального пользователя. Найди фактический путь проверки в auth; не предполагай существование Guard только по его названию в плане или примере.

Для нового защищённого маршрута аутентификацию и проверку ролей оформляй Guards. Сначала устанавливается подтверждённый пользователь, затем проверяются права. Отсутствующая, истёкшая или отозванная сессия означает 401; подтверждённый пользователь без необходимых прав — 403. CSRF — отдельная проверка для cookie-аутентифицированных мутаций, её нельзя заменить RolesGuard.

`X-Session-User`, если используется, проверяет совпадение ожидаемой личности с пользователем cookie, но не подтверждает её сам. Значения role/userId из props, заголовков, body и локального кеша не являются доказательством прав. Для роли используй актуальные данные сервера; скрытая кнопка не защищает endpoint.

Для «своего заказа», отзыва или другой личной записи роль USER недостаточна: проверяй владельца по подтверждённому пользователю и условиям запроса к БД. Не позволяй клиентскому userId выбирать владельца создаваемой записи. Политику 403 или 404 при обращении к чужой записи определяй по контракту сценария, не раскрывая лишних данных.

Смена роли или отзыв сессии должны влиять на следующий защищённый запрос. Не добавляй кеш прав или JWT с ролью без обсуждения срока актуальности и механизма отзыва. Изменение хранилища сессий — отдельная задача, а не побочное действие рефакторинга контроллера.

## Данные и конкурентные операции

Prisma schema и SQL-миграции вместе определяют ограничения БД. Валидация DTO помогает клиенту, но не заменяет уникальность, внешние ключи и CHECK в БД. Предварительный find перед create не исключает конкурентное создание: обрабатывай итоговое нарушение ограничения.

Объединяй взаимозависимые записи в транзакцию; выбирай блокировки или иной механизм конкуренции для конкретного инварианта. Обычная транзакция сама по себе не устраняет все гонки. Не держи её открытой во время внешних сетевых запросов. Не заменяй проектный механизм withLocks без изучения его поведения.

Цены хранятся целыми числами в минимальных денежных единицах; проверяй диапазон БД. Ограничивай выборку, пагинацию и сортировку по потребности сценария, избегай запросов в цикле, если связанные данные можно получить одной выборкой. Не меняй публичный формат списка ради оптимизации без согласования.

Порядок создания миграций, запрет изменения сгенерированного клиента и изоляция тестовой БД определены в [AGENTS.md](../../../../AGENTS.md), [руководстве БД](../../../../docs/DATABASE_GUIDE.md) и [правилах тестов](../../../../docs/TESTING.md). Используй эти источники, не дублируй процедуры здесь.

## Примеры применения

- «Добавить создание товара для ADMIN»: сначала определить владельца ProductsController, DTO, серверные значения, последовательность Guards и ошибки; при смешанном текущем контроллере обсудить разделение затронутой части. Не добавлять Redis или управление ролями.
- «Добавить личные заказы»: определить ресурс заказов и проверку владельца; не ограничиваться Roles(USER). Границы транзакции зависят от согласованных правил оформления заказа.
- «Перенести контроллер без изменения поведения»: проверить маршруты, DI, Guards и фактические HTTP-контракты, а не только сборку.
- «Создать или уточнить skill»: менять инструкции и справочники; пример ProductsController не разрешает рефакторинг приложения.
