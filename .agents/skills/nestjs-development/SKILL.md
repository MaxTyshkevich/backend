# Разработка NestJS backend

Используй этот навык для архитектурных решений в данном backend. Порядок работы задают [AGENTS.md](../../../AGENTS.md) и [backend-workflow](../backend-workflow/SKILL.md); здесь они не дублируются. Навык не разрешает менять приложение вне согласованной задачи. Для самостоятельной задачи о документации или Git технический справочник не требуется.

## Перед реализацией

1. Установи фактические версии NestJS и Prisma по package.json и lock-файлу. Проследи маршрут запроса от bootstrap и контроллера через сервис до БД. Существующий код — источник текущего поведения, но не автоматический образец архитектуры.
2. Назови ресурс, его владельца и границы ответственности: контроллер, сервис, модуль, зависимости и публичный HTTP-контракт. Для архитектуры, API, данных или доступа прочитай соответствующий раздел [references/architecture.md](references/architecture.md).
3. Если существующий класс смешивает ресурсы, предложи разделение затронутой части до добавления новой ответственности. Объясни пользу и цену; не расширяй согласованный объём молча. Технический долг за пределами задачи зафиксируй отдельно, без автоматического рефакторинга.
4. В плане укажи поведение, ошибки и проверки, а также совместимость URL, ответов и потребителей. Новые зависимости и слои добавляй для конкретной потребности, а не для формального соответствия шаблону.

## Основные решения

- Группируй функциональность по предметным областям. Внутри области разделяй HTTP-контроллеры по ресурсам: товары — ProductsController, категории — CategoriesController. Это соглашение проекта, а не требование NestJS «одна таблица — один модуль».
- Контроллер принимает валидированный ввод, вызывает сценарий сервиса и оформляет HTTP-ответ. Бизнес-правила и границы транзакций принадлежат сервису. Зависимости получай через DI, экспортируй только необходимые провайдеры.
- Для изменяющих запросов явно определяй разрешённые поля DTO; для ответов — публичную структуру и сериализацию. Тип TypeScript не заменяет runtime-валидацию и не исключает секретные поля из JSON.
- Проверяй сессию и необходимые права на сервере для каждого защищённого запроса. Роль и идентификатор из браузера не подтверждают доступ. Отличай роль от владения конкретной записью.
- Сохраняй выбранные технологии проекта: Prisma, PostgreSQL и cookie-сессии. Не вводи JWT, Redis, отдельный repository-слой или новую систему авторизации только потому, что они встречаются в примерах.
- Разделяй документированное поведение NestJS, договорённости этого проекта и рекомендацию для конкретной задачи. Новые или сомнительные API сверяй с официальной документацией для установленной версии; не переноси примеры другой версии без проверки.

## Перед завершением

Проверь не количество классов, а результат: каждый класс имеет понятную ответственность; маршруты принадлежат нужным ресурсам; зависимости не образуют цикл; DTO, доступ и ответ согласованы; ограничения БД и конкурентные операции учтены.

Проверки выбирай через backend-workflow и [docs/TESTING.md](../../../docs/TESTING.md). Для изменения API проверяй фактические HTTP-ответы и состояние БД, для доступа — гостя, неподходящую роль и владельца, когда это относится к сценарию. Проверка сессии и роли должна оставаться рабочей после их изменения или отзыва. Для изменений только навыка достаточно проверки структуры, ссылок, UTF-8 и diff; не запускай БД ради Markdown.

В результате сообщи принятые архитектурные решения, фактические проверки и оставшиеся ограничения. Если задача — только создать этот навык, его примеры не являются разрешением переносить контроллеры или менять API.
