# Работа над Microfronts backend

Работай в репозитории apps/backend или другом checkout того же backend. Сначала прочитай AGENTS.md и относящуюся к задаче документацию. Этот навык не заменяет согласие пользователя и не расширяет объём задачи.

## Исследование и план

Проверь Git-статус, ветку и существующие изменения. Найди реальный путь выполнения запроса или операции: src/main.ts, модули, контроллеры, сервисы, Prisma schema и SQL-миграции по необходимости. Воспроизведи проблему доступными безопасными проверками. Объясни, что подтверждено, что остаётся предположением и какое поведение предлагается. Предложи короткий план с затронутыми контрактами, проверками, документацией и публикацией. До явного согласия не редактируй код, конфигурацию, тесты и миграции.

## Реализация

После согласования используй ветку задачи согласно AGENTS.md и указаниям пользователя. Сохраняй посторонние правки. При расхождении документации, тестов и кода уточни ожидаемый контракт, прежде чем менять его. Для HTTP проверь декораторы, DTO, ответы, cookies и статусы; для E2E учитывай, что Test.createTestingModule не запускает main.ts. Для данных проверь prisma/schema.prisma и SQL-миграции: ограничения могут быть только в SQL. Не редактируй сгенерированный src/generated/prisma.

Подробности читай по задаче, а не все сразу:

- PostgreSQL, миграции, локальная и тестовая БД: [docs/DATABASE_GUIDE.md](../../../docs/DATABASE_GUIDE.md).
- Jest, E2E и изоляция БД: [docs/TESTING.md](../../../docs/TESTING.md).
- Рабочий порядок и состав PR: [docs/DEVELOPMENT_WORKFLOW.md](../../../docs/DEVELOPMENT_WORKFLOW.md).

## Проверка и завершение

Выбери проверки по изменению и сверь команды с package.json и .github/workflows/ci.yml. Обычно код проверяют через npm run typecheck, npm run build и относящиеся к нему тесты. Для тестов с БД сначала подготовь microfronts_test через npm run db:test:up; npm test и npm run test:e2e запускай последовательно, поскольку они используют общий тестовый контур. npm run lint исправляет файлы, поэтому не запускай его для диагностики без согласованных правок. Для миграций соблюдай порядок проверки тестовой и локальной рабочей БД из руководства; облачную БД не обновляй автоматически.

Обнови поддерживаемую документацию при изменении поведения и проверь diff. Для Markdown ограничься проверкой содержания, ссылок, UTF-8 и git diff --check. Сообщи фактические результаты и ограничения.

Если публикация входит в согласованный объём, используй доступный общий навык github-pr для механики Git/GitHub CLI или выполни тот же процесс по AGENTS.md и шаблону PR. Не считай ветку или compare-ссылку готовым PR. При явном ограничении работы текущей веткой остановись после локальных изменений и проверок.
